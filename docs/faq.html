General

Product basics.

What does Security Automation Manager do?

It helps WordPress administrators roll out strict HTTP security headers. Content Security Policy is its most capable pillar -- it emits per-surface policies, injects nonces, collects browser reports, discovers sources, and requires administrator approval before new sources affect the policy. X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, and Strict-Transport-Security are simpler per-surface pillars alongside it; see Other pillars below. Reverse Tabnabbing, External Scripts, and Internal Script Integrity round it out as further protections that act on the page or its assets directly rather than emit a header; see Content rewrite protections.

Who is it for?

It is for site owners, agencies, managed service providers, and WordPress administrators who need a safer path from no CSP or weak CSP to a stricter policy.

Does it require deep CSP knowledge?

No, but users still need to understand the basic workflow: report-only first, collect evidence, approve required sources, reject unknown sources, then enforce one surface at a time.

What are surfaces?

Surfaces are separate parts of the site. The plugin uses frontend, admin, login, and API. Each surface can have its own mode and policy inventory.

Why not use one policy for the whole site?

Different parts of WordPress need different resources. A frontend page, login page, REST response, and admin screen do not have the same risk profile or resource requirements.

What are the minimum requirements?

WordPress 6.4 or later and PHP 8.1 or later.

Rollout

Safe deployment questions.

Will report-only mode block anything?

No. Report-only mode asks the browser to report what would have been blocked. It does not block the resource.

Can enforce mode break a site?

Yes. Enforce mode can block required scripts, styles, fonts, frames, media, form posts, and runtime API calls. Use enforce mode only after reviewing evidence.

Which surface should I enforce first?

Usually the frontend surface, after testing key public journeys. Login, API, and admin surfaces should follow only when there is enough evidence.

Should I enforce wp-admin?

Use caution. WordPress admin screens and plugins may emit inline code outside the normal script API. Keep a rollback path and monitor violations carefully.

What is the promotion gate?

It is a safety check before enforce mode. The surface must have approved source or hash inventory, must not have recent violations inside the configured window, and must not have an active temporary override.

Why is the enforce button blocked?

The promotion gate has failed. Check approved inventory, recent violations, and temporary override status for the surface.

How long should I stay in report-only mode?

Long enough to test real journeys and pass the configured violation-free window. For production sites, start with at least 24 hours. Complex sites may need longer.

Approvals

Source inventory and policy decisions.

Should I approve every discovered source?

No. Approve only sources that are necessary, expected, and narrow. Reject or investigate anything unknown.

What does high risk mean?

High-risk proposals usually affect script, style, connection, form, frame, or worker behaviour, or use broad patterns such as wildcards, cleartext HTTP, broad schemes, or unsafe CSP keywords.

Is a high-risk source always bad?

No. A payment provider, consent manager, or known application endpoint may be legitimate. High risk means the proposal deserves deliberate review.

What is evidence count?

It is the number of times the same source has been observed or refreshed. It can help distinguish recurring site behaviour from one-off noise.

What happens when I reject a source?

The decision is recorded with a required administrator reason, and the matching surface, directive, and host fingerprint is suppressed from future automatic proposals unless a later approval or undo becomes the newest decision.

What is the difference between reject and revert?

Reject is for a pending or denied source that should not be approved. Revert is for a previously approved source that should be withdrawn.

What does Undo do?

Undo appends a new audit decision that clears the latest approval or rejection and returns the source to pending. It does not delete the original ledger row.

Why did a rejected source appear again?

Check whether the directive, host, or surface changed. Suppression is based on the source fingerprint, not every possible variant of a service.

Violations

Browser reports and learning behaviour.

Where are violation reports stored?

They are stored locally in the WordPress database in the plugin violation reports table. Old reports are purged by the daily scan according to the configured retention period. The default is 90 days; zero keeps reports indefinitely.

Are reports sent to a third-party reporting service?

No third-party reporting service is used by default. Browsers post reports to the site REST endpoint registered by the plugin. Administrators can override the reporting server URL for proxy, CDN, or load-balanced sites; local learning only works when that URL routes back to the plugin report endpoint.

Why do violations appear in report-only mode?

That is expected. Report-only mode exists to show what would be blocked if the policy were enforced.

Why do I see connect-src violations after static scanning?

Static scans cannot reliably see runtime fetch, XHR, WebSocket, or EventSource calls. These are learned from real browser reports.

Why are some blocked URIs ignored as source candidates?

The plugin ignores non-host values such as inline, eval, data, blob, and about. Those are not normal host-source approvals.

Can violation reports be spoofed?

Browser reports are client-generated and should not be treated as trusted user input. The plugin validates content type, silently discards cross-origin document URIs, deduplicates reports, and rate-limits storage.

What does occurrence count mean?

It shows how often the same violation fingerprint has been seen. A high count often means a real repeated site behaviour rather than a single test.

Other pillars

X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, Strict-Transport-Security, and the four cross-origin/legacy headers.

What other headers does the plugin manage besides CSP?

X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, Strict-Transport-Security, Cross-Origin-Resource-Policy, Cross-Origin-Opener-Policy, Cross-Origin-Embedder-Policy, and X-Permitted-Cross-Domain-Policies. Each is configured per surface (frontend, admin, login, API) from its own page under the Security Automation Manager top-level menu.

Do these nine pillars have a report-only mode like CSP?

No. None of them do. Each header is either sent exactly as configured, or not sent at all -- there's no intermediate learning state to roll through.

Why don't they have a discovery workflow or automation like CSP does?

They're single-value or small-allowlist headers with nothing to discover: there's no equivalent of "external sources this page happens to load." CSP's discovery, risk-scoring, and approval workflow exist because a CSP policy has to enumerate every legitimate external host; these nine pillars don't.

Does X-Frame-Options duplicate CSP's frame-ancestors directive?

They overlap in browsers that support both, and CSP's frame-ancestors takes precedence there. X-Frame-Options remains useful as a fallback for older browsers that don't support frame-ancestors.

Why is Permissions-Policy limited to a handful of features?

The plugin ships a starter set of seven commonly-restricted features (geolocation, camera, microphone, fullscreen, payment, usb, autoplay) rather than the full W3C registry, and offers None, Self, or All rather than free-text origin lists -- deliberately narrower in scope than CSP's source model.

Is Strict-Transport-Security as safe to toggle as the other pillars?

Not quite -- it's one exception. Browsers cache the Max-Age you send and keep refusing plain-HTTP connections for that long even after you lower or remove the setting, and there's no report-only mode to rehearse a rollout with first. Start with a short Max-Age, confirm every surface and subdomain genuinely works over HTTPS, then increase it. Preload is even less reversible: once a domain is on browsers' built-in preload lists, removal can take months, so this plugin won't let you enable it until Max-Age and Include Subdomains already meet hstspreload.org's submission minimum.

Why doesn't Strict-Transport-Security do anything on my staging site?

This header is only ever sent over an HTTPS request. If a surface is still served over plain HTTP, enabling HSTS for it has no effect -- sending the header over HTTP would be meaningless to browsers and would misrepresent the site as HTTPS-only before it actually is.

Are Cross-Origin-Opener-Policy and Cross-Origin-Embedder-Policy as safe to toggle as the other pillars?

No -- they're the other exception, alongside Strict-Transport-Security. Cross-Origin-Opener-Policy's Same-Origin severs window.opener access from any cross-origin popup this site opens or is opened by, which can break popup-based OAuth/SSO login flows -- Same-Origin-Allow-Popups is usually the safer enforcing value if the site relies on those. Cross-Origin-Embedder-Policy's Require-Corp is the highest-risk value this plugin offers anywhere: it blocks any cross-origin subresource (fonts, embeds, ad tags) that doesn't explicitly opt in via a matching Cross-Origin-Resource-Policy header or CORS, and most third-party embeds don't opt in by default, so enabling it can silently break unrelated page content. Both admin pages show a warning notice above the picker for this reason. Test popup logins, payment flows, and embedded third-party content after changing either.

Do I need Cross-Origin-Embedder-Policy at all?

Probably not. It's only actually required for pages that need cross-origin isolation -- features like SharedArrayBuffer or high-resolution timers. Most WordPress sites don't use those and can safely leave this pillar disabled, or set it to Credentialless if some enforcement is wanted without the full breakage risk of Require-Corp.

What's the difference between Cross-Origin-Resource-Policy and Cross-Origin-Embedder-Policy?

Cross-Origin-Resource-Policy controls who may load this site's own resources cross-origin -- it's low risk and only affects other sites embedding content from here. Cross-Origin-Embedder-Policy controls what this site is allowed to embed from elsewhere, and is the higher-risk of the two.

Do I need X-Permitted-Cross-Domain-Policies?

Only in the sense that leaving it at the browser default is slightly more permissive than necessary. It's a legacy header from the Adobe Flash/Acrobat era controlling cross-domain policy file loading; Flash is dead, so None (the default this plugin recommends) simply closes an attack surface that no longer serves a purpose for a modern site.

I changed a value and nothing seems different. What now?

Check you changed the correct surface -- frontend, admin, login, and API are configured independently, the same as CSP. Then confirm with your browser's network inspector that the header is present on a fresh request; some caching layers can serve a stale response with the old header until the cache clears.

Content rewrite protections

Reverse Tabnabbing, External Scripts, and Internal Script Integrity.

How are these different from the header pillars?

None of them add a header. Reverse Tabnabbing and External Scripts rewrite the rendered HTML response; Internal Script Integrity adds an integrity attribute to script/stylesheet tags as WordPress builds them. All three are free, all three only act on requests they can act on safely (never wp-admin, login, AJAX, REST, XML-RPC, cron, or CLI requests for the two rewriters), and all three fail open -- any uncertainty leaves the page or tag untouched.

Can Reverse Tabnabbing break a link?

No. It only ever adds rel="noopener" to a target="_blank" link that doesn't already have noopener or noreferrer -- every other attribute, and any other rel tokens, are left exactly as they were.

Will enabling External Scripts break my analytics or embeds?

Not by default. A newly discovered script or stylesheet origin is always classified Unclassified, never Blocked -- and Report mode, the default, never removes anything at all, it only builds the inventory. Even Enforce mode only ever removes an origin you explicitly marked Blocked, or an Approved-immutable origin whose SRI hash no longer matches.

Does this plugin generate Subresource Integrity hashes for me?

For third-party scripts, no, and deliberately so -- computing a hash by fetching the remote URL would defeat the point of SRI, since a compromised origin would just have its tampered file hashed and trusted. "Approved -- immutable" only ever compares against a hash you paste in yourself, from a source you already trust. For your own theme/plugin/core files it's different: Internal Script Integrity (Scripts page, Internal tab) reads the exact local file this site is about to serve and computes its hash automatically, since there's no third party in that loop to defeat SRI's trust model.

What's stored in the External Scripts inventory?

Each row is keyed by origin -- scheme and host, e.g. https://cdn.example.com -- so entries stay deduplicated even for a CDN serving a different filename per request. The most recently observed full URL (path and query included) is also kept, so the "Suggest" hash helper has an exact file to fetch without you having to find that URL yourself. If a query string could contain something sensitive, be aware it may be retained in that field.

Does Internal Script Integrity need updating every time I update a plugin or theme?

No. The pinned hash is cached against the file's size and modification time; when either changes, the next request that serves the file recomputes the hash automatically. There's nothing to re-approve or re-paste.

Compatibility

WordPress, plugins, themes, and caching.

Is it compatible with caching plugins?

Usually, but nonce-based pages should not be served from a full-page cache unless the cache is nonce-aware or appropriate exclusions are configured.

Can it work with tag managers?

It can, but tag managers often load other scripts dynamically. Use report-only mode and approve only the hosts that are genuinely required.

Can it work with payment providers?

Yes, where the required scripts, frames, connections, and form actions are approved. Test checkout in report-only before enforcing.

Can it work with page builders?

Often, but page builders can introduce inline scripts, inline styles, external embeds, and runtime calls. Test representative pages before enforcing.

Does it add 'unsafe-inline'?

No. The nonce workflow is intended to avoid relying on 'unsafe-inline'.

What about older browsers?

Some reporting and CSP3 behaviour varies by browser. The plugin uses direct report-uri delivery by default for faster local learning, and can emit Reporting API headers when enabled in Settings.

WordPress.org build & pricing

What's free, what's paid, and the guideline posture.

Does the plugin work without payment?

Mostly, yes. All ten pillars, CSP's report-only rollout, discovery, violation reporting, policy-change review, and three of the four CSP automation modes (Manual, Automatic with medium+high approvals, Automatic with high approvals only) are free in every build, with no payment or remote entitlement checks. The exception is Fully Automatic CSP mode -- zero-review auto-apply -- which requires an active subscription: £1.99/month or £19.99/year. See the user guide's Automation tiers section.

What happens if I select Fully Automatic without a subscription?

The surface is quietly kept on Automatic (high approvals only) instead -- it doesn't fail, error, or partially apply. The Settings tab marks the option "(requires upgrade)" and, where a checkout flow is available in your build, shows an Upgrade button.

Does the plugin use a custom update endpoint?

The WordPress.org package does not poll a third-party update manifest or install updates from outside the WordPress.org update system. A separate GitHub-channel build does, for administrators who install from GitHub instead.

Does the plugin contact a licensing service?

Only if you use the Upgrade button to start a checkout for Fully Automatic mode, and only where that flow is available in your build. Nothing else described on this site contacts a third-party service for licensing, telemetry, or remote product configuration.

Are CSP reports sent to VCNS or another provider?

No. Browser CSP reports are posted back to this WordPress site's own REST endpoint and stored locally.

Are new CSP sources applied automatically?

Only if you've turned on one of the three free automatic modes, or the paid Fully Automatic mode -- and only within that mode's risk ceiling. On the default Manual mode, no.

Does manual automation mode change policy on its own?

No. Automation configuration defaults to manual mode on install and upgrade.

Privacy

What data exists and where.

What is stored locally?

Policy profiles, source inventory, hash inventory, violation reports, scan logs, audit log entries, policy versions, and policy change decisions are stored in the WordPress database.

Does normal CSP operation require telemetry?

No general telemetry is required for normal CSP operation. Browser reports are posted back to the site endpoint by default.

What leaves the site?

The WordPress.org package keeps CSP operation local and does not contact third-party services for plugin updates, telemetry, or remote product configuration. The only outbound call anywhere in the product is the Upgrade checkout flow for Fully Automatic mode, and only when an administrator deliberately starts it.

Troubleshooting

Fast answers during incidents.

My site broke after I enabled enforce mode. What should I do?

Return the affected surface to report-only. Review the Violations tab. Approve only the required sources or hashes. Retest before enabling enforce mode again.

I cannot access wp-admin after changing CSP. What now?

Use an alternative administrator route or database access to return the admin surface to report-only. Then review recent violations and policy changes.

The manual scan finds no sources. Is that wrong?

Not necessarily. Static scans see rendered HTML and linked CSS. Runtime-only activity may appear only through browser violation reports.

How do I report a security vulnerability?

Do not report suspected vulnerabilities in public issues. Use the repository security policy and the private reporting route described there.
